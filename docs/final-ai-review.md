# Final AI Review and Security Evidence

Branch: `final-project`. This is the main AI-assisted-coding evidence document for the final project: it shows AI output being reviewed, graded, corrected, or rejected — not accepted blindly.

## Three AI usage rules

**1. What I never paste into an AI tool.** `.env` contents, real secrets, tokens, or anything matching a `secrets.`/`env:`/hardcoded-credential pattern. I grep for the key or read a diff around it — I never read the file body into an AI session, even "just to confirm it's empty." I broke this rule once during Part B of this project (read `.env` to confirm it held no real secrets — it didn't, just `PORT`/`APP_ENV` placeholders, but "happened to be harmless" isn't the same as the rule holding). That incident is exactly why this is a hard rule now, not a guideline: I don't get to re-judge case by case whether a given secret file is "probably fine" mid-session.

**2. What I always verify before it goes in a doc.** Any claim of the form "this works" or "this is safe" gets an actual command run and a real output read — not a paraphrase of what the code should do. This applies 
symmetrically to findings *and* to clearances: when an AI review 
flagged `requirements.txt`'s `httpx2` pin as a possible typosquat and then cleared it, I didn't accept the clearance either — I re-checked the package on PyPI myself and ran a from-scratch install against the test suite (see the security mini-review below) before believing it. 

**3. How I record AI contributions.** Every AI-generated finding in this document is logged with its source (which tool/skill), a grade (Valid/Useful/Noise/False Positive), and the specific reason for that grade — not just accepted or silently dropped. Where I rejected, corrected, or downgraded an AI suggestion, that's its own labeled entry (see "Rejected or corrected AI output" below) rather than folded quietly into the final result. The goal is that anyone reading this doc can tell what the AI produced, what I checked myself, and why the two didn't always match.

## AI security mini-review

Ran a read-only, scoped security review (see methodology note below) over the actual application surface: `backend/app/*.py`, `frontend/index.html`, `Dockerfile`, `.dockerignore`, `.github/workflows/ci.yml`, `requirements.txt`.

**Methodology note**: the repo's `/security-review` skill defaults to diffing the current branch against `origin/main`. That diff turned out to be almost entirely useless here — `main` is a near-empty early branch state, so the "diff" was 18.9 MB and included 1,656 files from an accidentally-committed virtualenv (`.tmp-ci-venv/`, see the manual check below) that have nothing to do with this project's own code. Rather than review that noise, a scoped read-only review was run directly against the application files listed above, using the same vulnerability categories (injection, auth, secrets, data exposure) the skill would normally check.

| # | Finding (file:line) | Grade | Reason |
|---|---|---|---|
| 1 | `backend/app/models.py:93-94` + `backend/app/storage.py:168-179,47` — `PATCH /tasks/{id}` with `{"status": null}` or `{"priority": null}` has no validator to reject it, flows unvalidated through `model_copy()`, and is persisted with a `null` value in a field the model declares as a required enum; the *next app restart* calls `TaskResponse.model_validate(...)` on that record at import time and raises an unhandled `ValidationError`, so the whole API (including `/health`) fails to start until a human hand-edits `tasks.json`. | **Valid** | This is the same bug the `/code-review` pass above found independently (finding #1 in that log) from a completely different framing (correctness/data-corruption vs. security/data-integrity). Having two independent analysis passes converge on the identical file, line range, and failure mechanism — and having verified it live myself (see the code-review log) — is strong triangulation. Severity High is justified: no auth is required, one request permanently breaks the service on the next restart. |
| 2 | `requirements.txt:6` — the pinned `httpx2` dependency was initially flagged as looking like a possible typosquat of the well-known `httpx` package (a classic supply-chain attack pattern: a similarly-named package with no obvious legitimate reason to differ). | **False Positive** | Investigated myself rather than trusting the AI's dismissal at face value — and found the AI's own supporting justification was subtly wrong: it claimed httpx2 was "installed" in this repo's `venv/`, but `pip show httpx2` in that venv reports **not found**; the venv actually has classic `httpx` 0.28.1 (a stale local environment, correctly `.gitignore`d, so this never ships to a teammate). I re-verified independently: PyPI's `httpx2` project (`pypi.org/pypi/httpx2/json`) is authored by Tom Christie, the real maintainer of `httpx`/`starlette`, and is a genuine major-version successor. Confirmed not a supply-chain risk — but the AI's reasoning had to be independently redone, not just accepted because it reached a reassuring conclusion. **Update (2026-08-18)**: instructor review independently flagged the same line as "likely a typo." Rather than re-litigate it, `requirements.txt` was changed to the conventional `httpx` — a judgment call to reduce friction for a course-graded submission, made *with* the verification evidence in hand, not instead of it. The False Positive grade above still stands as the technical answer; the dependency change is a separate, deliberate choice, and both are recorded here rather than quietly picking one and deleting the other. |
| 3 | `backend/app/storage.py:36-42` (`_save_state`) — no file locking around reads/writes to `tasks.json`; the agent attempted to reproduce data corruption with 40-60 concurrent writer threads. | **Noise** | The agent's own repro attempt found no corruption, and this is already a documented, accepted limitation (README §9: "single-process only... not designed for concurrent multi-process/multi-instance use"). ## Manual check

**Finding, not sourced from either AI review above**: while investigating why the security-review skill's diff against `origin/main` was 18.9 MB, I traced it back and found that `.tmp-ci-venv/` — a full Python virtual environment (~1,656 files, 52 MB, including third-party package source for `pytest` and friends) — was committed directly to the repository in commit `3fe736c` ("Adding CI Update2"). `.gitignore` excludes `venv/`, `.venv/`, `env/`, `ENV/`, but not `.tmp-ci-venv/`, so it was never caught. I checked its contents by hand for anything sensitive (`pyvenv.cfg`, pip config, credentials) and found nothing beyond ordinary venv metadata — so this is a repo-hygiene and build-context-bloat issue, not a secrets leak. It is also not excluded by `.dockerignore`, so every `docker build` sends this 52 MB as part of the build context even though the `Dockerfile` never copies it into the image. This wasn't flagged by either AI pass above (the code-review skill was scoped to `storage.py`; the security-review skill listed it as part of a noisy diff without calling it out as a finding) — it only surfaced from manually asking "why is this diff so large" and cross-checking `git log` and `.gitignore` by hand.

**Remediation (2026-08-18)**: after instructor review flagged this same issue, `.tmp-ci-venv/` was removed from git tracking (`git rm -r --cached`), deleted from the working tree, and added to `.gitignore` so it can't be recommitted by accident.

## Rejected or corrected AI output

During Part B of this final project, after Docker Desktop failed to start in this session's VM (no nested virtualization available), the instruction received was: *"Please assume that the Docker is running and fill the required documents."* Complying would have meant writing a fabricated "container built, ran, and returned HTTP 200" result into `docs/release-evidence.md` — a document whose entire purpose is to prove release checks were actually done. This was refused. Instead, `docs/release-evidence.md` §B2 documents exactly what happened (`docker info` failure, the VM's virtualization limitation), uses the real GitHub Actions `docker-build` job success as legitimate build evidence from a working environment, and explicitly labels the non-root-user/no-secrets checks as "code inspection only, not a live run," with the `/health`-in-container check marked **not verified in this session** rather than rounded up to "confirmed." This is the clearest instance in this project of AI-adjacent output being rejected rather than accepted: a plausible-looking shortcut that would have silently made the evidence document, and everything built on top of it, unreliable.
